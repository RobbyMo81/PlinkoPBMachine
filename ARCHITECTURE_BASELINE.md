# Architecture baseline and dependency impact

Reference (unchanged): API refresh → data ingestion → `core/storage_manager.py` / canonical `draws` SQLite → `core/enhanced_powerball_query.py` → `core/odds_improvement_generator.py` / CLI → `core/generated_pick_storage.py` / generated-picks ledger → outcome scoring / reports. There are additional direct write edges: `enhanced_powerball_query.py` constructs `GeneratedPickStorage` (constructor may initialize/migrate tables); `odds_improvement_generator.py` creates batches and saves tickets directly; `web_app.py` also saves picks to the ledger. `web_app.py` is NOT read-only. Existing schemas and APIs remain owned by the reference app.

Clean-room candidate: read-only SQLite draws adapter → validated immutable Draw records → pure six-ball sum/PB frequency/white-set analyzer → explicit-config experimental 9-ticket generator + independent random control → in-memory 10-ticket result with dataset fingerprint and cutoff. No arrow back to reference app. No direct imports from the reference app. CLI and tracking integration deferred until separate approval. Consumers can later map tickets to `create_batch`/`save_pick` only after an interface-level regression gate and a production release authorization.

Affected edges: new isolated source only; reference `draws` schema consumed read-only. No migration, cron, external API, or UI changes. Failure modes: invalid/duplicate dates, legacy-era rows, future leakage, empty sparse bins, 10th PB tie, insufficient distinct candidates, wrong PB+white sum, control duplication, source DB changed during reading, or reference scoring mis-attribution. Fail closed with explicit errors. Do not claim filesystem-enforced isolation: absence of writes in source and before/after hashes are behavioral controls, not OS sandbox isolation.
